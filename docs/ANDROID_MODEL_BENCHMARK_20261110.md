# S24 Ultra 실제 모델 비교 · 2026-11-10

현재 앱의 세 모델을 실제 S24 Ultra(SM-S928N, SM8650, Android 16)에서 비교했다. 같은 현장 복합 질문 12개, 공통 문맥 4,096, 최대 출력 2,048토큰, GPU 요청으로 총 36회 직접 생성했다. 제품의 빠른 문서 본문 조립 경로를 생성 성능으로 계산하지 않았다.

**긴 한국어 설명을 만드는 능력은 E2B가 상대적으로 나았다. 그러나 E2B도 원문 수치와 비교 결과를 바꾸었으므로, 이 결과를 현장 답변의 정확도 검증 완료나 출시 승인으로 해석할 수 없다.** 270M과 1B의 현재 설치 파일·SDK·설정도 장문 답변용 대체 모델로 채택하기 어렵다. 아래 속도는 실패·단편·반복 출력을 구분해서 읽어야 한다.

## 본시험 측정값

| 시도 | 12 | 12 | 12 |

| 빈 출력·실행 오류 | 0 | 4 | 12 |
| 전체 처리 중앙값 | 73.91초 | 15.71초 | 38.03초 |

- 전체 처리는 모델 준비와 생성이 끝나거나 실패할 때까지의 시간이다. 1B의 15.71초를 정상 장문 답변의 완료 시간으로 사용하면 안 된다. 빈 출력·다섯 글자 단편·반복 붕괴가 포함된 중앙값이다.
- 첫 표시 가능 본문은 `AnswerMarkdown.preview`가 완결된 접두부를 반환한 시점이다. 제목만 먼저 나온 경우도 포함하며, 첫 네이티브 토큰이나 실제 화면 프레임 표시 시간과 다르다.
- 문자 수는 앱의 UTF-16 문자열 길이 기준이며 공백·Markdown·반복 문자도 포함한다. 길다고 유용한 답변이라는 뜻이 아니다.
- SDK의 토큰 벤치마크가 활성화되지 않아 정확한 입력/출력 토큰 수·tokens/s·출력 한도 도달 여부는 미측정이다. 요청한 최대 2,048토큰을 실제 사용량으로 기록하지 않았다.
- 최대 출력 전에 모델이 종료하거나 남은 문맥이 제한될 수 있다. 미완성 출력의 종료 원인은 이번 SDK 통계만으로 확정하지 않는다.

## 실제 답변 검토

동일한 세부 질문·원문 패킷을 사용했음을 결과 파일 간 대조했다. 질문별 필수 항목 3개에 0/0.5/1점을 주고, 중요한 사실 오류·반복·형식 문제를 별도로 기록했다. 점수는 이 개발 질문 묶음에 대한 Codex의 수동 검토이며 독립 평가자의 판정이나 모델 정확도 백분율이 아니다. [고정 검토표](validation/android-model-field-rubric-20261110.json) · [36개 수동 검토](validation/android-model-field-review-20261110.json).

폰의 **설정 → 모델 성능 비교**에도 36개 통합 보고서를 저장했다. 화면의 정확함 통과는 모든 필수 항목 충족·중요 오류 없음·완결된 형식을 기준으로 적용했으며 이번에는 모두 수정 필요로 표시했다. 일부 내용을 유용하게 설명한 부분 점수는 별도 수동 검토 JSON에서 확인할 수 있다. 기존 보고서는 백업했다.

### Gemma 4 E2B

문장·단계·표를 만들어 12문항 모두 텍스트를 반환했지만, 다음과 같은 원문 불일치가 있었다.

- 작업 투입 전 질문에서 소수점을 빠뜨리고, 기준 미만인 측정값을 초과로 잘못 비교했다.
- 일산화탄소 영향 표에서 농도와 시간을 바꾸거나 가스 이름을 혼동했다.
- 구조·응급처치 질문에서 원문의 횟수·속도를 다르게 반복했다.
- 여러 답변에서 신고 번호 오타, 깨진 출처 ID, 표 열 수 불일치, 미완성 체크리스트가 나타났다.

수치·조건이 있는 현장 판단을 모델 생성 결과에 바로 맡길 수준은 아니다. 숫자를 반복해서 재생성하는 긴 표와 체크리스트는 특히 원문 대조가 필요하다. 구체적인 오류와 원문은 검토 파일에 남겼다.

### Gemma 3 1B

GPU에서는 4개가 빈 출력이고, 텍스트가 반환된 나머지도 단편·별표/음절 반복·잘못된 농도 기준이 나왔다. 분량만으로 정상 응답을 판정할 수 없었다. CPU 진단에서도 첫 현장 질문의 수치를 바꾸고 표·문구를 반복했다. 현재 한국어 복합 현장 질문에서 E2B를 대체할 근거가 없다.

### Gemma 3 270M

GPU에서 12개 모두 빈 출력이었다. 앱 프로세스 로그에는 `Invalid decode and sample result`와 샘플 토큰을 0으로 바꾼다는 네이티브 경고가 반복됐다. 이 실패를 모델 독해력 점수와 동일하게 취급하지 않는다. CPU에서는 텍스트가 반환됐지만 질문 재진술이나 짧은 수락문으로 끝나 실제 질문에 답하지 못했다. 현재 파일·SDK·한국어 프롬프트 조합의 결과이며, 모든 환경에서 이 모델이 실행되지 않는다는 결론은 아니다.

## 검색 입력에서도 확인된 한계

세 모델의 근거 패킷은 동일했지만 패킷 자체가 항상 충분하지는 않았다. CO 질문에는 헤모글로빈 결합 기전 문단이, 용접 질문에는 작업 중 계속 환기하는 관련 절이 선택되지 않았다. 다른 질문에서는 범위 밖 준비 절과 도식 노이즈가 들어갔다. `missingEvidenceQueries`가 비어 있어도 의미적으로 모든 필수 조건이 선택됐다는 보장은 없다.

따라서 검색 입력 누락, 원문 데이터 노이즈, 생성 모델의 숫자 변경·판단 오류를 분리해서 개선해야 한다. 모델 교체만으로 이번 문제 전부가 해결된다고 볼 수 없다.

## CPU 재시험: 같은 첫 현장 질문

본시험과 같은 첫 질문·근거·공통 지시·문맥·출력 한도로 CPU 재시험을 한 번씩 진행했다. 아래는 12문항 평균이 아니며 답변 길이와 내용도 서로 다르므로 연산 처리량의 단순 배수로 해석하지 않는다.

| 모델 | GPU 본시험 첫 문항 | CPU 재시험 | CPU 출력 | 확인한 결과 |
| --- | ---: | ---: | ---: | --- |
| E2B | 65.74초, 3,245자 | 191.11초 | 3,544자 | 네 측정값의 수치 비교는 맞았지만 질문 상황 재진술 오류·환기 절차와 마지막 표 미완성이 남음 |
| 1B | 7.31초, 빈 출력 | 110.93초 | 3,155자 | 기준값 변경·황화수소 누락·표/문구 반복·측정값만으로 안전하다고 서술 |
| 270M | 38.26초, 빈 출력 | 5.59초 | 15자 | “네, 한국어로 답하겠습니다.”만 반환 |

E2B의 이번 CPU 답변에서 수치 비교가 개선됐다는 사실만으로 CPU가 항상 정확하거나 GPU가 항상 틀린다고 결론내리지 않는다. 생성 변동·백엔드 수치 차이·가열·실행 조건의 영향을 분리할 반복 검증이 필요하다. 1B는 CPU에서도 중요한 수치를 잘못 생성했으므로 장문 품질 문제 전부를 GPU만의 문제로 설명할 수 없다.

### 짧은 질문과 NPU 진단

본시험 외에 총 13회 진단을 실행했다. 짧은 두 질문도 실제 공통 앱 프롬프트를 사용하므로 영어 문장만을 입력한 순수 영어 모델 시험은 아니다. 모두 현재 앱의 한국어 안내 지시가 포함돼 있다.

- 270M GPU는 짧은 두 질문에서도 빈 출력을 반환했다. 따라서 긴 근거 입력만으로 빈 출력을 설명할 수 없다. CPU에서는 질문 재진술·주제 오인·짧은 수락문이 나왔다.
- 1B는 한국어 세 문장 질문에서 CPU 3.69초, GPU 4.18초로 짧은 관련 문장을 생성했다. 다른 표현에서는 주제 오인이나 반복이 있었으므로 이 두 시간을 정확한 현장 답변 성능으로 확대하지 않는다.
- 1B의 NPU 우선 요청 두 번은 실제로 GPU가 실행됐다. 첫 요청에서 `Unsupported dispatch runtime version`·`No usable Dispatch runtime found` 오류와 텐서 할당 실패가 확인됐고, NPU 프로세스 종료 후 GPU로 전환됐다. 두 번째는 같은 실행의 실패 기록에 따라 GPU를 사용했다. **NPU 속도 측정 성공이 아니며, 이번 초기화 오류의 GPU 전환 동작만 관찰했다.** [해당 프로세스 로그](validation/model-comparison-20261110/npu-native-diagnostic.txt).
- 추가 진단과 본시험은 질문·출력 한도·모델 파일·실행 문맥이 달라질 수 있어 통계를 합치지 않았다. 특히 현재 NPU 파일의 1,280 문맥 한도는 본시험의 최대 2,048 출력에 충분하지 않다.

## 선택에 대한 판단

현재 앱과 설치 파일에서 다음 개발의 기준 모델은 **E2B를 유지**하는 편이 타당하다. 270M·1B로 바꾸면 한국어 복합 현장 질문의 설명 품질이 개선된다는 근거가 없었다. 다만 E2B의 긴 직접 생성도 수치 변경·비교 오류·미완성 출력이 있어 그대로 현장 판정에 사용하면 안 된다.

빠른 문서 본문과 수치·단위·비교 조건은 검색 결과 및 명시적 규칙으로 보존하고, 모델의 보충 설명은 원문과 맞는지 검증하는 구조가 필요하다. 긴 답변을 강제하는 것만으로 정확도와 사용자 경험이 좋아지지 않았다. 이번 결과를 근거로 모델·백엔드의 평소 설정을 자동 변경하지 않았다.

## 장문 지연 원인 추가 계측

문맥 4,096·최대 출력 2,048·질문·근거·지시를 유지하고 두 질문에서 기본 실행과 추측 생성 해제를 비교했다. 출력 한도를 줄이는 변경은 하지 않았다. SDK 0.17.1의 실험용 벤치마크 플래그를 계측 프로세스에서 활성화해 실제 토큰 통계를 얻었다. 앞선 36회 본시험은 이 플래그가 꺼져 있었으므로 해당 기록의 미측정값을 소급해서 채우지 않는다.

| 질문 | 기본 전체 시간 | 추측 생성 해제 | 실제 출력 토큰 | 기본 decode 속도 | 해제 decode 속도 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 여러 가스 측정값과 작업 투입 전 점검 | 58.36초 | 58.87초 | 양쪽 모두 1,823 | 35.71 tokens/s | 35.16 tokens/s |
| 여러 출입구의 구조 장비 배치 | 42.96초 | 49.23초 | 양쪽 모두 1,397 | 34.05 tokens/s | 29.17 tokens/s |

두 비교 모두 질문·근거 해시가 같고 생성 원문도 완전히 같았다. 반복·수치 오류도 유지됐다. 두 번째 실행의 발열이나 순서 영향은 통제하지 않았으므로 해제가 원인인 성능 악화라고 단정하지 않지만, 개선을 보여준 결과는 아니다. **이 후보 설정은 제품에 적용하지 않았다.** 기존 출력 설정과 채팅 기록, 36개 비교 보고서도 그대로 유지했다.

이 두 사례에서는 입력 2,070/2,334토큰에 이어 1,823/1,397토큰을 생성했다. 초기화와 입력 처리를 줄이더라도 본문 생성 시간이 많이 남는다. 처음 일부 텍스트가 빨리 나오는 것과 장문 전체의 완성 시간을 구분해야 한다.

라이브러리 누락 경고도 조사했다. 해당 SDK의 공식 코드는 동적 OpenCL 샘플러를 찾지 못하면 정적으로 연결한 OpenCL 샘플러를 먼저 시도한다. 따라서 `libLiteRtTopKOpenClSampler.so`가 없다는 경고 하나만으로 CPU 샘플링이나 지연 원인을 확정하지 않았다. [정확한 버전의 샘플러 구현](https://github.com/google-ai-edge/LiteRT-LM/blob/v0.17.1/runtime/components/sampler_factory.cc).

플래그는 새 엔진을 만들 때 읽는 실험 API이며 시험 종료 후 원래 값으로 복구했다. [공식 플래그 정의](https://github.com/google-ai-edge/LiteRT-LM/blob/v0.17.1/kotlin/java/com/google/ai/edge/litertlm/ExperimentalFlags.kt) · [4회 추가 계측 JSON](validation/gemma-decoding-path-20261110/summary.json). 시험 코드는 `app/src/androidTest/java/com/minyook/sllm2/GemmaDecodingPathBenchmarkTest.kt`다.

## 측정 범위와 재현

실행 순서는 270M → 1B → E2B이며 모델 사이 30초 대기했다. USB 연결 중 배터리 온도는 시작 시 각각 26.6°C, 32.9°C, 35.8°C였고 E2B 종료 시 39.7°C였다. E2B 질문 시작 시 Android 발열 상태는 1~2였다. 충분히 냉각한 교차 순서 반복시험이 아니므로 속도를 모델 고유의 절대 성능이나 일정한 실사용 시간으로 일반화하지 않는다.

모델의 첫 질문은 새 엔진 초기화를 포함하고 다음 질문은 가능한 경우 엔진을 재사용한다. 저장된 디스크 캐시는 유지했으며 기기 전체의 완전한 콜드 부팅 시험은 아니다. 문서 검색 준비·UI 프레임·음성 인식/낭독·통신·가스 경보 동작은 생성 계측에 포함하지 않는다. 가용 시스템 RAM은 기록하지만 모델의 최대 메모리 사용량을 정밀 측정한 결과는 아니다.

기존 모델·채팅 기록을 지우지 않았고, 실행 설정은 메모리에만 주입했다. 세 본시험의 설정 불변 검사가 통과했다. 기존 비교 보고서는 `tmp/model-benchmark-20261110/previous-device-comparison.json`에 백업했다. 네트워크 추론이나 추가 모델 다운로드 없이 설치된 가중치로 실행했다.

| 프로젝트 루트 기준 경로 | 역할 |
| --- | --- |
| app/src/androidTest/java/com/minyook/sllm2/FieldModelComparisonTest.kt | 설정 화면과 같은 비교 실행기 호출, 별도 CPU/GPU/NPU 진단 |
| app/src/main/java/com/minyook/sllm2/model/FieldComparisonSuite.kt | 12문항·공통 지시·근거 검색어·출력 설정 |
| app/src/main/java/com/minyook/sllm2/model/ModelComparison.kt | 생성 시간·출력·공통 근거·오류 기록 |
| tools/summarize-model-comparison.py | 조건·질문·근거 일치 검증, JSON/CSV/전체 답변 집계 |
| docs/validation/model-comparison-20261110/ | 본시험 원본·요약·CSV·답변·추가 진단 |
| tmp/model-benchmark-20261110/ | 빌드·계측 로그와 원본 백업 |

설치된 모델 파일은 E2B 2,588,147,712바이트, 270M 304,005,120바이트, 1B 584,417,280바이트였다. 270M과 1B는 양자화와 실행 파일도 다르므로 모델 크기만의 효과를 분리한 실험이 아니다. SDK는 LiteRT-LM 0.17.1이다.

집계 재현 명령은 프로젝트 루트에서 실행한다.

```powershell
python tools/summarize-model-comparison.py tmp/model-benchmark-20261110/measured tmp/model-benchmark-20261110/field-gpu-gemma3-270m-20261110.json tmp/model-benchmark-20261110/field-gpu-gemma3-1b-20261110.json tmp/model-benchmark-20261110/field-gpu-gemma4-e2b-20261110.json
```
