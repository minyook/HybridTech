# iPhone 모델 적재·연속 질문 중 종료 분석

작성/갱신: 2026-10-20. 이전 Gemma 종료 로그와 보완 이력, 이후 Apple 경량 로컬 경로를 구분합니다.

## 2026-10-21 문서 답변 보완과 메모리 경계

문서 검색·발췌 편중과 짧은 생성 보고를 반영해 페이지/절차별 입력을 균등하게 배분하고, AI 정리와 문서 상세 발췌를 구분해 표시합니다. 정리 기본 한도는 512로 바꾸며 **문맥 2,048·prefill 64·단일 엔진 수명은 유지**합니다. 상세 발췌는 모델에 추가로 생성시키지 않습니다. 반복 목록과 길이 종료의 미완성 끝 문장을 정리하고 SDK의 실제 사용량/길이 종료 신호를 그대로 보존합니다.

구체 구현은 [경량 설계](IPHONE_LIGHT_AI.md), PC에서 사용자 두 질문을 보낸 결과는 [검증 기록](../../web/docs/validation.md)에 구분합니다. 실제 iPhone의 수정 후 답변 품질·전체 메모리 성공을 의미하지 않습니다. 기존 모델과 이전 v1 설정은 보존하며 재다운로드는 필요하지 않습니다.

## 최신 변경: Apple 경량 로컬 경로

기존 Gemma 적재/질문에서 highwater 종료가 반복되어 iPhone/iPad는 **Qwen3 0.6B q4f16_1 / WebLLM 0.2.86**으로 별도 실행합니다. PWA와 기기 내 실행을 유지하며 서버 추론은 추가하지 않습니다. 기존 Gemma 파일/설정/대화/작업은 보존하고 Apple에서 해당 대형 파일을 자동 적재하지 않습니다. PC·Android는 기존 경로를 유지합니다.

다운로드 총량 353,285,213바이트, 문맥 2,048 고정, 출력 기본 512/선택 256, prefill 64, 실 토크나이저 근거 예산, 순차 검증 저장과 캐시 전용 생성입니다. [경량 설계와 파일 경로](IPHONE_LIGHT_AI.md) · [새 시험 순서](../IPHONE_TEST.md). 아래 Gemma 파일 구간 읽기·배치 1·GPU 수명 설명은 그 이전 변경 이력입니다.

Windows Chromium에서 모델 런타임 WASM 힙 160MiB를 관찰했으나 GPU·별도 토크나이저·전체 WebContent 측정이 아닙니다. 기존 Gemma의 1,347.1MiB 관찰과 비교해 전체 프로세스 개선율을 계산하지 않습니다. 작은 모델에서 심폐소생술 압박 절차 누락도 관찰되어 원문 전환을 유지합니다. **실제 iPhone 13 Pro의 경량 모델 안정성·메모리 상한·생성 품질은 아직 검증하지 않았습니다.**

## 실제 종료 로그에서 확인한 사실

사용자가 제공한 `JetsamEvent-2026-10-20-104352.ips`를 로컬에서 분석했습니다. 기록 시각은 2026-10-20 10:43:52 +0900, OS는 iPhone OS 27.0.1입니다. 이전에 전달된 10/16·iOS 18.6.2 로그는 이번 오류의 근거로 사용하지 않습니다. 원본 로그·고유 기기/사건 식별자·다른 앱 목록은 저장소에 포함하지 않습니다.

| 대상 | 기록의 종료 사유 | `rpages` | `pageSize` | 계산한 사용량 |
| --- | --- | --- | --- | --- |
| WebKit WebContent 기록 A | `highwater` | 216,384 | 16,384바이트 | 3,381MiB, 약 3.30GiB |
| WebKit WebContent 기록 B | `highwater` | 135,735 | 16,384바이트 | 약 2,120.86MiB, 2.07GiB |

Apple 문서는 `highwater`를 시스템 프로세스가 기대 메모리 사용량을 초과한 경우로 설명하고 `rpages × pageSize`로 바이트 사용량을 계산합니다. 근거: [Jetsam 해석](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports), [기기에서 로그 가져오기](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs).

따라서 **이 로그의 WebContent 종료 사유는 높은 메모리 사용량으로 확인**했습니다. 다만 로그에는 Field Guard URL·JavaScript 할당 스택·실행 문맥 값이 없습니다. 사용자 재현 시각/동작과의 연관을 바탕으로 분석하며, 위 두 항목을 동시에 존재한 두 엔진으로 단정하거나 메모리를 합산하지 않습니다. 3.30GiB를 해당 기기의 고정 한도로 해석하지도 않습니다. GPU 프로세스의 기록 사용량이 작다고 해서 GPU 공유 메모리의 영향을 배제할 수는 없습니다.

## 12:20:58 질문 생성 중 종료 로그 추가 분석

추가로 받은 `JetsamEvent-2026-10-20-122058.ips`의 기록 시각은 **2026-10-20 12:20:58.39 +0900**, OS는 iPhone OS 27.0.1, pageSize는 16,384바이트입니다. 사용자는 모델 준비 완료 뒤 질문 전송 시 종료됐고 재실행의 중단 단계가 `decode`라고 확인했습니다. 아래 시스템 기록과 사용자 재현을 함께 해석하며, 원본/고유 식별자/다른 앱 목록은 저장소에 추가하지 않습니다.

| 항목 | 새 로그 값 | 해석 |
| --- | --- | --- |
| `largestProcess` | `com.apple.WebKit.WebContent` | 기록에서 가장 큰 프로세스 |
| 종료된 WebContent의 `reason` | `highwater` | 기대 메모리 사용량 초과로 시스템이 종료 |
| `rpages` | 177,169 | 2,902,736,896바이트 = 2,768.265625MiB = 약 **2.703GiB** |
| `lifetimeMax` | 177,176 | 2,768.375MiB = 약 **2.703GiB** |
| WebContent의 highwater 기록 수 | 1개 | 두 엔진의 동시 실행으로 단정할 근거가 없음 |

근거는 원본 20행(pageSize), 4,859행(rpages), 4,869행(WebContent), 4,878행(reason), 4,880행(lifetimeMax)입니다. Apple 공식 해석대로 페이지 수에 페이지 크기를 곱했습니다. **이 로그의 WebContent 종료는 이제 추정이 아닌 메모리 사용량 초과로 확인**했습니다. 사용자 재현과 시각을 바탕으로 Field Guard의 질문 생성 중 종료와 연결하지만, 로그 자체에는 사이트 URL·프롬프트·사용한 앱 빌드·저장 토큰 값·할당 스택이 없습니다. 정확한 WASM/GPU/JS 비중이나 특정 SDK 할당 원인은 여전히 확정하지 않습니다.

이전 10:43:52 기록의 3.30GiB/2.07GiB와 새 2.703GiB를 합산하지 않습니다. 서로 다른 실행·조건이므로 메모리 개선율로 계산하지 않으며 **2.703GiB를 이 기기의 고정 브라우저 한도로 안내하지 않습니다.** 새 기록의 GPU 프로세스 수치가 작다고 공유 GPU 메모리의 영향을 배제하지도 않습니다. PC에서 측정한 WASM 힙 용량과 이번 실제 iPhone의 WebContent 사용량도 다른 지표입니다.

코드 이력상 엔진/Worker 교체는 11:46:56의 `212488e`, 명시적 GPU 장치 파괴·로컬 진단은 12:38:13의 `8be6b00`입니다. **12:20:58 로그는 마지막 GPU 정리·진단 변경 전 사건**이므로 그 마지막 변경의 성공/실패를 증명하지 않습니다. 또한 로그에는 빌드 해시가 없어 당시 PWA에 `212488e`가 실제 적용됐다고 단정할 수도 없습니다. 이 시각 차이를 마지막 변경이 문제를 해결했다는 근거로 사용하지 않습니다.

현재 결론은 다운로드나 토큰 할당량 소진 문제가 아니라 **해당 WebContent의 실행 메모리 초과**입니다. 답변 뒤 정리는 한 답변 생성 중의 최대 사용량까지 낮추지 못합니다. 같은 모델 재다운로드나 반복적인 복구 선택을 추가 해결로 권하지 않습니다. 현재 모델·PWA 요구를 유지한 상태의 실기기 안정화는 아직 미해결이며, 모델/엔진의 실행 메모리를 더 줄일 수 있는지 별도 검증이 필요합니다. 이번 분석에서 런타임 설정이나 모델을 임의로 변경하지 않았습니다.

## 파일 읽기 경로에서 바꾼 부분

이전 1MiB 입력 제한은 파일의 한 번 읽기 크기를 제한합니다. 고정된 `@litert-lm/core` 0.18.0의 `ReadableStreamDataStreamWrapper`는 별도로 건너뛴 구간과 보존할 구간을 JS 슬라이스에 저장하고 C++가 요청한 바이트를 WASM에도 복사합니다. 일부 구간을 나중에 다시 읽기 위해 보관하는 경로이므로 입력을 작게 나누는 것만으로 이 중간 캐시를 제거하지는 못합니다. 해당 캐시가 실제 iPhone 종료의 유일한 할당 원인이라고 확정한 것은 아닙니다.

새 Apple 모바일 경로는 SHA-256 확인을 거친 같은 로컬 파일의 필요한 구간을 직접 읽습니다. `readAndPreserve`는 파일을 그대로 보존하므로 이후 다시 읽을 수 있고, `readAndDiscard`/`discard`는 별도 JS 구간 캐시를 만들지 않습니다. 대형 요청도 1MiB 이하로 나누어 WASM에 복사하고 각 비동기 읽기 뒤 새 힙 뷰를 가져옵니다. 임의 오프셋·되감기·32비트 포인터·범위·중첩 읽기·파일 오류를 처리합니다. 이 방식은 **중간 JS 구간 캐시를 피하지만 WASM/GPU의 모델·작업 공간을 제거하거나 전체 메모리를 1MiB로 제한하지 않습니다.**

SDK의 공개 `Engine`/대화 API, GPU_ARTISAN, 공식 E2B 파일·해시와 문서 근거는 유지합니다. 모델 변환·재다운로드·서버 추론·원격 질문 전송은 추가하지 않습니다. 데스크톱/일반 스트림은 기존 SDK 경로를 사용합니다.

## 첫 답변 후 두 번째 질문 중 종료

파일 구간 읽기 수정 이후 사용자는 실제 iPhone 홈 화면 앱에서 첫 답변에 성공했고, 두 번째 질문 **‘심폐소생술 알려줘’**에서 페이지가 다시 열리며 **‘답변 토큰 생성 완료를 확인하지 못해’**가 표시됐다고 보고했습니다. 이는 `decode` 단계의 완료 표시가 없다는 뜻입니다. 이 새 사건의 로그는 아직 없으며 위 10:43:52 로그를 두 번째 질문 종료의 직접 증거로 사용하지 않습니다. 누적 할당, 새 질문의 최대 작업 공간 또는 다른 GPU/런타임 원인 중 무엇인지 확정하지 않았습니다.

기존 구현도 질문마다 conversation을 삭제했지만 엔진과 Worker/WASM 힙은 유지했습니다. Apple 모바일에서는 한 엔진이 한 답변만 생성하도록 변경했습니다. 스트림과 SDK 사용량을 받은 뒤 `conversation.delete()`와 `engine.delete()` 완료를 기다리고 `done`을 보냅니다. 메인 런타임은 해당 Worker를 종료해 이전 WASM 실행 범위를 없애고 다음 질문용 엔진 하나를 자동으로 준비합니다. 단순 conversation 삭제로 WASM 힙 용량이 줄었다고 가정하지 않습니다. SDK 삭제 의미의 근거: [공식 Engine API](https://developers.google.com/edge/litert-lm/js), [고정 버전 conversation.delete](https://github.com/google-ai-edge/LiteRT-LM/blob/v0.18.0/js/packages/core/src/conversation.ts).

준비 중 들어온 질문은 같은 `prepareAI` Promise를 기다립니다. 이전 Worker의 늦은 메시지는 버리고, 준비 중 질문 취소가 새 엔진의 초기화 표시를 지우지 않도록 합니다. 정리 중 강제 종료는 `cleanup`(AI 메모리 정리)로 구분합니다. 데스크톱은 기존 엔진 재사용을 유지합니다. 저장 모델·대화·토큰 선택은 보존하며 서버 추론·모델 변경·페이지 새로고침을 추가하지 않습니다. **각 답변 뒤 모델 준비 시간이 필요할 수 있으며 즉시 응답을 보장하지 않습니다.** 엔진 삭제와 Worker 종료가 실제 기기의 모든 GPU 할당을 즉시 반환한다고 측정한 결과도 아닙니다.

관련 경로는 `web/src/ai/worker-engine.ts`(SDK 정리 순서), `runtime.ts`(Worker 교체·단일 자동 준비·질문 대기), `recovery.ts`(정리 단계), `web/tests/worker-engine.test.ts`·`ai-runtime.test.ts`·`ai-recovery.test.ts`(회귀 검사)입니다.

## 준비 완료 뒤 질문 전송 시 decode 종료 재발

엔진 수명 분리 수정 뒤에도 사용자는 준비가 끝난 상태에서 질문 보내기를 누르면 ‘문제가 반복적으로 발생했습니다’가 나타나며 다음 실행의 안내가 **답변 토큰 생성**이라고 확인했습니다. 따라서 질문 화면을 여는 것만으로 종료되는 사례로 분류하지 않습니다. `decode`는 첫 텍스트 수신 이후의 지속 표시이므로 새 시스템 로그 없이 정확한 할당이나 종료 원인을 단정하지 않습니다. 10:43:52의 `highwater`는 앞선 사건의 증거이며 이번 사건 자체를 확정하는 로그가 아닙니다.

모델 초기화는 가중치/엔진 준비이고 실제 대화의 입력·생성·토큰별 작업 공간은 이후 사용됩니다. 준비 성공과 답변 성공은 다릅니다. 답변 뒤 Worker를 교체하는 조치는 앞선 엔진의 수명을 줄이지만 **한 답변 생성 중의 최대 메모리**를 보장하지 않습니다. 토큰 설정 축소나 같은 파일 재다운로드를 반복하는 것으로 해결됐다고 판정하지 않습니다.

고정 SDK 0.18.0은 엔진 삭제와 별도로 `liteRtLmWasm.preinitializedWebGPUDevice`에 GPU 장치를 보관합니다. SDK의 `LiteRtLm.delete()`는 이 버전에서 no-op입니다. Apple 정상 종료에는 엔진 삭제 뒤 이 장치의 `destroy()`를 명시하고, 그 다음 Worker를 종료합니다. 엔진 삭제가 실패해도 GPU 장치 정리를 시도합니다. 강제 종료·취소에서 모든 장치 메모리가 즉시 반환된다고 보장하지 않습니다. 이 누락을 고친 것만으로 현재 `decode` 종료의 원인이 밝혀졌다고 주장하지 않습니다.

`web/src/ai/worker-resources.ts`는 SDK가 공개한 실제 런타임의 WASM 힙 용량을 engine/engine-ready/conversation/prefill/decode/metrics/cleanup에서 표본 수집하고 장치 손실과 미처리 GPU 오류의 종류를 관찰합니다. 생성 중에는 첫 스트림 청크와 이후 32청크마다 기록하며 이는 토큰 수 측정이 아닙니다. `web/src/ai/diagnostics.ts`는 설정값과 시각·실행 버전을 함께 최대 48개만 localStorage `fieldguard-ai-diagnostics`에 남깁니다. 질문·답변·원시 오류·주소·기기 식별자는 저장하지 않고 허용된 필드만 내보냅니다. 설정의 **AI 진단 기록 저장**으로 JSON을 받을 수 있으며 원격 수집은 없습니다.

**WASM 힙 용량은 실제 상주 메모리·GPU 버퍼·WebContent 전체 메모리가 아닙니다.** GPU 오류가 없다는 기록 역시 OS 메모리 종료를 배제하지 않습니다. 새 기록은 앞으로의 실행부터 수집하므로 이전 사건의 최대 사용량을 소급해 계산하지 않습니다. 해당 종료 시각의 새 Jetsam/WebKit 기록과 함께 분석해야 합니다.

## 검증 범위

자동 검증과 Windows Chromium에서의 실제 E2B 결과는 [검증 기록](../../web/docs/validation.md)을 따릅니다. PC의 최대 파일 읽기 1MiB 관찰은 iPhone 전체 메모리 사용량이나 개선율을 뜻하지 않습니다. 실제 iPhone의 첫 답변 성공은 사용자 보고입니다. 새 12:20:58 로그에서는 WebContent의 약 2.703GiB highwater 종료를 확인했으며 **마지막 GPU 정리 수정 이후의 실기기 연속 성공은 아직 확인하지 않았습니다.**

재시험 시 서버를 켠 상태로 홈 화면 앱을 한 번 열어 업데이트를 받고 같은 주소의 모든 Field Guard 화면을 완전히 닫았다가 다시 엽니다. 설정의 **‘답변이 끝나면 AI 메모리를 정리하고 다음 질문을 자동으로 준비해요’** 문구를 확인합니다. 기존 모델과 현재 토큰 선택을 유지하고 첫 답변 완료 뒤 ‘심폐소생술 알려줘’, 이어서 세 번째 질문을 보냅니다. 준비 중에는 기다렸다가 처리되는지 확인합니다. 같은 종료가 반복되면 새 시각의 로그로 비교하며 반복 실행을 계속하지 않습니다.
