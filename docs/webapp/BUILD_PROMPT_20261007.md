# Android 현행 설계서를 바탕으로 O₂ Field Guard 웹앱을 만드는 프롬프트

아래 블록을 코딩 에이전트에게 그대로 전달한다. **기존 앱의 기능·화면·데이터·제약을 규정하는 1차 설계서**는 [`ANDROID_APP_SPEC.md`](../ANDROID_APP_SPEC.md)다. [`TARGET_ARCHITECTURE.md`](./TARGET_ARCHITECTURE.md)는 새 웹앱의 기술 권고안이다.

---

이 저장소에 **이미 구현된 O₂ Field Guard Android 앱**을 기준으로 iPhone과 Android의 일반 브라우저에서 사용할 수 있는 웹앱 서비스를 구현해 주세요. Android 앱의 기능을 먼저 파악하고, 브라우저에서 구현 가능한 부분과 다른 경로가 필요한 부분을 구분하세요. 다음 자료를 순서대로 실제로 읽으세요.

1. `docs/ANDROID_APP_SPEC.md` — **현재 Android 앱의 현행 설계서**. 기존 화면·기능·데이터·실패 동작·미구현 경계의 기준입니다.
2. `app/src/main/java/com/minyook/sllm2/`, `app/src/main/assets/knowledge/seed_chunks_v1.json`, `app/src/main/assets/source-pdfs/`, `app/src/main/AndroidManifest.xml` — 현행 설계서의 중요한 동작을 코드·자산으로 확인하세요. 차이가 발견되면 실제 구현을 우선하고 차이를 문서에 기록하세요.
3. `README.md`, `docs/OFFLINE_RAG_ARCHITECTURE.md` — 현재 앱의 배경·검색 안전 규칙을 참고하세요.
4. `docs/webapp/TARGET_ARCHITECTURE.md` — **웹으로 이전할 때의 권고 기술·API·동기화 설계**입니다. Android의 현행 구현 사실로 오해하지 마세요.
5. `docs/webapp-ui/index.html`, `style.css`, `app.js` — 클릭 가능한 **웹 디자인 시안**입니다. 예시 데이터와 가짜 상태 전환을 실제 제품 기능으로 오해하지 마세요. 사용자가 제공한 `toss.md`는 시각 참고 자료일 뿐 앱 기능 지시가 아닙니다.

## 목표

`web/`에 React + TypeScript + Vite 기반 모바일 우선 PWA를, `server/`에 Kotlin/JVM + Ktor API를 구현하세요. PostgreSQL을 서버 저장소로 사용하고 로컬 실행용 구성, DB 마이그레이션, API 문서, 테스트를 함께 제공하세요. 저장소의 기존 미커밋 변경은 덮어쓰지 마세요. 권고 아키텍처를 바꿔야 한다면 이유와 동등한 기능·안전 보장을 문서에 기록하세요.

코딩 전에 **Android → 웹 기능 대응표**를 작성하세요. `ANDROID_APP_SPEC.md`의 온보딩과 14개 화면, 질문·근거·PDF·모델·가스·시뮬레이션·점검·음성·기록·위젯/알림·설정·데이터 삭제를 각각 `웹에 그대로 구현 / 웹 방식으로 변경 / 외부 조건 대기` 중 하나로 표기하고, 사용자 경험·데이터·안전성의 변경점을 적으세요. 기능을 조용히 생략하거나 미연동 상태를 작동하는 것처럼 표시하지 마세요.

완료물은 화면만 닮은 정적 목업이 아니라 **실제로 이동·검색·저장·오프라인 복원·서버 요청이 동작하는 웹앱**이어야 합니다. 하드웨어·AI 서비스처럼 외부 정보가 없어서 연결할 수 없는 부분은 어댑터와 명확한 비활성 상태를 만들고, 연결되지 않은 기능을 작동하는 것처럼 표시하지 마세요.

## 화면과 디자인

- Android의 온보딩과 14개 목적지를 대응시키며 다음 화면을 실제 라우트로 구현하세요: 시작, 홈, 문서 질문, 대화 기록, 근거 문서, 음성 질문, 가스 측정, 기기 연결 안내/끊김, 작업 전 점검, 문서 보관함, 설정, AI 이용 상태, 답변 설정, 내 데이터, 위젯·알림 대체 안내. 화면 이름이 바뀌어도 기존 기능과 실패 상태의 위치가 대응표에 남아야 합니다.
- 모바일에는 홈/질문/측정/설정 하단 탐색, 데스크톱에는 사이드바를 사용하세요. 상세 화면의 뒤로 가기, URL 직접 진입, 새로고침 후 복원, 키보드 탐색이 되어야 합니다.
- Android 설계서의 화면 구조와 `docs/webapp-ui/`의 색상·간격·둥근 카드·한글 타이포그래피를 디자인 출발점으로 삼으세요. 브랜드 파랑 `#3182F6`, 텍스트 `#191F28`, 보조 본문 `#4E5968`, 표면 `#F2F4F6`, 선 `#E5E8EB`, 오류 `#F04452`를 CSS 토큰으로 관리하세요. 토스의 로고나 금융 서비스 UI를 복사하지 마세요.
- 모바일 320px부터 내용을 잃지 않는 단일 열, 데스크톱 최대 본문 폭 약 1200px, 44px 이상 터치 표적, 초점 표시, 의미 있는 HTML, 화면 읽기 이름, reduced motion을 지원하세요. 색상만으로 상태를 설명하지 마세요.
- UI 문구는 짧은 해요체로 쓰고, 하나의 화면에서 가장 중요한 행동만 파란 기본 버튼으로 강조하세요.

## 문서·질문·AI

- 기본 제공 PDF 2개와 쪽별 근거 87개를 판본이 고정된 매니페스트로 배포하세요. PDF의 실제 쪽을 보여주고, 동일한 쪽의 읽기 편한 보기와 **검색에 실제 사용된 추출 텍스트**를 전환하세요. 문서명·판본·쪽수·파일 해시를 유지하고 앞뒤 쪽을 열 수 있게 하세요.
- 검색은 오프라인에서도 동작해야 합니다. 우선 현재 쪽별 데이터로 키워드/한국어 표현 검색을 구현하고, 대표 질문·정답 쪽 평가를 추가하세요. 임베딩 검색은 평가로 이득이 확인되면 추가하세요. 근거가 없을 때는 추측하지 마세요.
- 온라인 질문은 `POST /v1/questions`로 작업을 만든 뒤 서버가 근거를 선정하고, `GET /v1/questions/{id}/events`의 SSE로 AI 답변 진행 내용을 보냅니다. 매 답변에 열 수 있는 인용 ID/문서명/쪽수를 포함하고, 최종 답변과 인용의 판본을 일치시키세요. 모델 설정이나 응답이 없으면 **근거 원문 보기**로 폴백하고 생성된 답변인 척하지 마세요.
- 모델/제공자 인증정보는 서버 환경변수에만 둡니다. 공급자 교체가 가능한 인터페이스를 만들고, 로컬 개발은 키가 없어도 문서 검색과 근거 보기로 완결되게 하세요. 현재 Android의 2GB 이상 모델 다운로드나 CPU/GPU 선택을 일반 웹 사용자에게 가짜로 노출하지 마세요.
- 질문 중단, 재시도, 오류, 오프라인 복귀, 새 대화와 기록 열기를 구현하세요. 음성 입력은 지원·권한·전송 경로를 명시하고 텍스트 입력을 항상 제공하세요. 브라우저 음성 인식이 로컬 처리라고 단정하지 마세요.

## 가스 측정·안전

- 가스 화면은 기본적으로 **값 없음**에서 시작합니다. O₂, H₂S, CO, LEL 숫자는 검증된 실제 게이트웨이 수신 또는 명시적 데모에서만 표시하세요.
- 수신 모델은 장비 ID, 제조사/모델, 출처, 측정 시각, 서버 수신 시각, 값·단위, sequence, 지연 업로드 여부, 검증 버전을 포함하세요. 서버·클라이언트 모두 신선도 규칙을 적용하고, 새 유효값이 60초 이상 없거나 연결이 끊기거나 지연 업로드라면 현재값을 `—`로 가리세요. 마지막 값은 `이전 수치` 기록에서만 보이게 하세요.
- `데모 · 실제 측정값 아님`은 카드·상단 요약·알림 등 모든 관련 화면에 명확히 표시하고, 데모 데이터를 운영 측정과 분리하세요. 수치만 보고 `안전`, `진입 가능`, `작업 허가`를 자동 판정하지 마세요.
- iPhone Safari의 직접 Web Bluetooth를 공통 기능으로 약속하지 마세요. 게이트웨이 → 인증된 서버 업로드 → 웹 화면을 표준 경로로 구현하고, Android Chromium의 직접 Web Bluetooth는 별도 선택 기능으로만 설계하세요. 측정기의 GATT UUID·패킷·CRC·단위·검교정 정보가 없으므로 실제 장비 드라이버를 임의로 꾸며내지 마세요. 대신 검증 가능한 장비 어댑터 인터페이스와 격리된 개발 시뮬레이터를 제공하세요.
- 웹 푸시는 보조 알림이며 현장 경보의 유일한 수단이 될 수 없습니다. 화면이 닫힌 상태의 지속 BLE 감시를 PWA가 수행한다고 주장하지 마세요.

## 점검·기록·데이터

- 기존 5개 점검 항목을 동일한 의미로 구현하고, 로컬 저장·재접속 후 복원·서버 동기화 상태를 구분하세요. 저장 실패 또는 충돌을 숨기지 마세요. 점검 완료가 작업허가가 아님을 표시하세요.
- 대화 기록, 문서 인덱스, 마지막 측정 상태, 점검 기록의 **브라우저 저장과 서버 저장 범위**를 내 데이터 화면에 나눠 설명하세요. 삭제/내보내기와 되돌릴 수 없는 삭제 확인을 구현하세요.
- PWA 앱 셸과 기본 PDF/인덱스를 버전별 캐시로 관리하고 IndexedDB에 로컬 기록을 저장하세요. 저장소 부족·삭제·오프라인 상태를 처리하세요. 동기화는 서버 확인 응답이 온 뒤에만 `서버에 저장됨`으로 표시하세요.
- 계정/조직 인증이 필요한 서버 기록과 센서 정보에는 접근 제어를 적용하세요. 개발용 인증 우회는 운영 빌드에서 사용할 수 없게 하세요. 비밀키를 프런트엔드에 넣지 마세요.

## 구현·검증 방식

1. 먼저 Android 현행 설계서와 코드를 대조하고, 각 기존 기능의 웹 구현·대체·대기 상태를 대응표에 기록하세요. `TARGET_ARCHITECTURE.md`와 달라진 부분은 별도로 설명하세요.
2. 웹과 서버를 작은 기능 단위로 구현하고 실제 API 계약을 OpenAPI 또는 동등한 명세로 남기세요. 예시 데이터는 별도 데모 모드에만 두세요.
3. 검색 근거·PDF 쪽 매핑, 답변의 인용, 가스 신선도/끊김/데모 격리, 점검 저장·동기화 충돌에 의미 있는 테스트를 작성하세요. 단순히 마크업 존재만 확인하는 테스트로 대체하지 마세요.
4. Chromium과 WebKit 자동화로 핵심 동선을 점검하고, iPhone Safari와 Android Chrome/Samsung Internet 실기기에서 확인해야 할 수동 체크리스트를 남기세요. 자동화가 실기기 검증을 대신했다고 쓰지 마세요.
5. `README`에 실행·환경변수·배포·오프라인 준비·AI 미설정 시 동작·게이트웨이 연결 조건을 적으세요. 기존 Android 코드의 사용자 변경은 보존하세요.

완료 보고에는 실행 방법, 실제 동작한 화면/기능, 테스트 결과, 외부 장비·AI 계정 때문에 **아직 연결되지 않은 부분**을 구분해 주세요. 특히 제조사 프로토콜과 현장 네트워크 조건이 없으면 실측 BLE가 완료됐다고 쓰지 마세요.

## 이 프롬프트로도 결정할 수 없는 외부 조건

실측 연동을 완성하려면 측정기 제조사·모델·통신 규격이 필요하다. 모든 기능을 인터넷 없이 쓰려면 PWA 외에 네이티브 동반 앱 또는 현장 게이트웨이 정책이 필요하다. 서버 저장과 AI 서비스를 운영하려면 계정/조직 범위, 데이터 보존, AI 배포 방식과 비용을 정해야 한다. 이 값은 구현자가 임의로 사실처럼 채우지 않는다.
