# Android 대화 맥락·선택 항목 복구

2026-11-05 후속: 대화 기록 전달만으로 수량 질문의 대상/속성이 해석되지 않던 사례를 수정했다. 최신 대상·속성 전환과 생성 지연 정책은 [대화 초점 설계](ANDROID_DIALOGUE_FOCUS.md)를 참고한다. 아래는 11월 4일 구현/검사 이력이다.

갱신: 2026-11-04. 같은 Android 대화 안에서 이어 묻는 질문을 처리하는 변경이다. 모델 학습이나 인터넷 동기화 기능이 아니다.

## 확인한 원인

- 이전 질문 한 개를 일부 지시어 앞에 붙이는 방식이었으며, 이전 답변·선택 항목·여러 턴의 주제를 사용하지 않았다.
- ‘또 다른 건 없어?’와 ‘항목이 안 보이는데?’를 독립 문서 질문으로 검색해 문서 부재/되묻기로 보내는 문제가 있었다.
- 검색 결과의 선택 항목 배열이 비어도 ‘아래에서 선택’ 안내가 나왔고, 작성 중에는 버튼을 숨겨 본문 안내와 화면 상태가 맞지 않았다.
- LiteRT 대화 객체를 매번 새로 열면서 실제 최근 대화도 프롬프트에 전달하지 않았다.

## 현재 처리

1. `FieldGuardViewModel`이 현재 열린 채팅의 완료된 메시지만 `ConversationTurn`으로 변환한다.
2. `ConversationContext`가 최근 최대 16메시지 안의 주제·이전 답변·실제 선택 항목을 확인한다. 새 주제, 짧은 후속 질문, 추가 근거, 쉽게/자세히 설명, 번호/항목 선택, 항목 표시 문제, 이전 사용자 진술 회상, 단순 응답을 구분한다.
3. 검색은 해석된 독립 질문으로 수행한다. 예를 들어 ‘산소 유해가스 측정방법 → 그럼 언제 해야 해? → 누가 해야 해?’는 측정방법 → 측정시기 → 측정자 자격으로 주제를 좁힌다. 매번 이전 질문 전체를 재귀적으로 이어 붙이지 않는다.
4. ‘다른 내용’은 같은 주제의 문서 후보를 검색해 이미 표시한 본문과 비교한다. 새 근거가 있을 때만 추가하며 조건/예외를 포함한 범위는 유지한다. 새 근거가 없으면 **추가 근거를 못 찾았다고 안내**하고, 이미 찾은 문서가 없다는 안내나 임의 일반 지식 생성으로 바꾸지 않는다. 단, 앞선 답변부터 일반 지식이었고 현재도 문서 검색을 완료해 일반 지식 경로로 판별한 경우에는 최근 대화를 모델에 넘겨 일반 설명을 이어 간다.
5. ‘항목이 안 보인다’는 이전 선택지를 본문 번호 목록과 버튼으로 다시 표시한다. 예전 대화에 실제 선택지가 저장되지 않았다면 기존 주제의 현재 문서 결과에서 실제 항목을 복구한다. 항목을 확정하지 못했으면 대상/조건을 물으며 없는 목록을 가리키지 않는다.
6. ‘2번’, ‘두 번째’, 실제 항목 이름은 이전에 제공한 `SearchSuggestion.question`으로 연결한다. 범위를 벗어난 번호는 실제 목록을 다시 안내한다.
7. ‘아까 뭐라고 말했지?’는 기기 안에 저장된 사용자 진술을 인용한다. 과거 진술을 현재 측정값이나 승인 사실로 바꾸지 않는다.
8. 일반 지식/문서 보충이 필요한 경우 최근 대화의 사용자/답변 역할과 이번 사용자 원문을 프롬프트에 전달한다. 화면에 보이는 사용자 문장은 검색용 해석 문장으로 교체하지 않는다.

후속 질문 해석은 보수적인 언어/문맥 규칙이며 모든 자연어를 완벽하게 재작성하는 별도 LLM은 아니다. 다른 구체적 주제가 나타나면 검색 주제를 새로 잡으며, 명시적인 ‘다른 얘기: …’ 이후에는 뒤따르는 질문의 모델 문맥에서도 앞선 주제를 제외한다. 현재 현장의 승인/실측값은 대화 기록으로 확정하지 않는다.

## 저장·메모리·예산

- 기존 `local_chat_history`에 `topicQuestion`, `answerStatus`를 선택 필드로 추가했다. 기존 `resolvedQuestion`, 출처 ID, 선택 항목도 유지한다.
- 기존 데이터에 새 필드가 없어도 열리며, 가능한 경우 앞선 실질 질문으로 주제를 복구한다. 현재 저장 한도는 기존과 같은 **20개 채팅·채팅당 80메시지**다.
- 다른 채팅으로 이동/새 채팅 생성 시 그 화면의 메시지만 사용한다. 채팅을 합쳐 검색 DB에 넣거나 문서 임베딩으로 저장하지 않는다.
- 생성 프롬프트에는 최근 최대 **3쌍**의 역할이 표시된 JSON을 넣되 문맥·출력 예산·UTF-8 바이트 상한으로 제한한다. 긴 답변은 문장 중간에서 잘라 조건을 없애지 않고 해당 답변 전체를 생략하며 `assistantOmitted`를 표시한다. 실제 제목이 있으면 최대 6개의 제목만 `discussedHeadings`로 전달해 이미 다룬 주제를 알리며, 이 제목 목록은 완전한 사실/조건 설명으로 취급하지 않는다. 여유가 없으면 대화 JSON을 생략하고 해석된 현재 질문을 사용한다.
- LiteRT 네이티브 KV 대화를 계속 누적하지 않는다. 기존 엔진 수명/검색 모델과의 메모리 교대 정책을 유지하면서 필요한 텍스트만 전달한다. 작은 문맥에서 모든 이전 답변을 모델에 넣는다는 보장은 하지 않는다.

## 선택 항목 표시

`SearchResolution.withVisibleChoices()`는 다음 두 조건을 보장한다.

- 실제 선택지가 있으면 본문에도 번호/이름을 넣어 버튼이 화면 밖에 있어도 읽을 수 있다.
- 실제 선택지가 없으면 ‘아래 항목을 선택’이라는 안내를 사용하지 않는다.

작성 중에도 선택 버튼은 보이며 답변 완료 전에는 비활성화한다. 복구·회상·추가 없음 응답은 ‘대화 이어가기’로 표시한다. 선택 항목을 복사해서 버튼처럼 보이게만 만들지 않고 실제 요청 질문과 연결한다.

## 검증과 실기기 확인

기존 고정 150개 질문·추가 24개도 문맥 해석 입구를 통해 다시 평가한다. 별도 연속 대화는 측정방법 → 시기 → 자격 → 추가 내용 → 항목 복구 → 심폐소생술 → 반복 시점 → 호흡 회복 → 커피로 주제 전환 → 쉽게 설명의 10단계다. 실질 문서 내용/기존 정답 기준을 고치지 않는다.

최종 수치·APK 해시·실제 본문은 `docs/validation/android-conversation-20261104.json`과 `docs/validation/android-conversation-examples-20261104.md`에 기록한다. PC 검색 모델/JVM/빌드 검증이며 **기기 미연결로 실제 Gemma 연속 생성·Compose 터치·음성 실발화는 별도 실기기 확인이 필요**하다. 전체 사실 정확도나 무제한 장기 기억을 검증한 결과는 아니다.

설치 후 같은 채팅에서 재현한다. 기존 대화를 이어 보아도 되고 새 채팅에서 다음을 차례로 입력해도 된다.

1. 산소 유해가스 측정방법
2. 그럼 언제 해야 해?
3. 누가 해야 해?
4. 또 다른 건 없어?
5. 항목이 안보이는데?
6. 번호나 항목 이름으로 선택

모델·문서 재다운로드나 앱 데이터 삭제는 필요하지 않다. 웹/PWA·AP 통신 기능은 변경하지 않는다.

최종 검사: JVM 회귀 128개 통과/선택 실행 10개 제외, 실패 0개. 앞선 전체 실행에서 실제 모델 평가를 포함한 129개 검사와 고정 150개·추가 24개·10단계 연속 문서 대화가 통과했다. 마지막 두 모델 문맥 보완은 최종 회귀 검사로 확인했다. Lint 오류 0개/경고 118개. 실제 생성·UI 조작은 미실행이다.
