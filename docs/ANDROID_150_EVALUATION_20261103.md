# Android 150개 질문 실행 결과 · 2026-11-03

현재 Android 앱의 `QuestionSearchCoordinator`와 `DocumentAnswerPlan`을 PC JVM에서 실행했다. 검색 모델은 앱에 포함된 EmbeddingGemma 300M q4 가중치를 사용하고, 앱의 `SemanticTokenizer`가 만든 토큰 ID로 실제 CPU 추론했다. 기존 150개 질문·정답 페이지·필수/금지 표현은 수정하지 않았다.

## 결과

| 구분 | 기존 자동 기준 통과 | 전체 |
|---|---:|---:|
| 단일 질문 | 80 | 90 |
| 표현 변형 | 26 | 30 |
| 복합 질문 | 20 | 20 |
| 문서 밖 질문 | 10 | 10 |
| 합계 | 136 | 150 |

**136/150을 전체 답변 정확도로 해석하지 않는다.** 문서 밖 10개는 관련 없는 문서를 붙이지 않았는지 검사한 결과다. 그중 9개는 일반 지식 생성 대상으로 분류됐지만 Gemma 답변은 이번에 생성하지 않았다. 나머지 1개는 실제 작업 승인 상태를 문서로 추측하지 않는지 검사했다.

문서 질문 140개 중 기존 자동 기준 통과는 126개다. 이 중 8개는 필요한 내용이 본문에 있어도 뒤에서 추가 확인을 요구한다. **자동 기준 통과와 추가 확인 없는 문서 답변을 모두 충족한 항목은 118/140개**다. 이 역시 개발 질문 집합에 대한 자동 검사이며 독립된 신규 질문 품질 점수나 전문가 검수 결과가 아니다.

## 실패 14개와 추가 확인 8개

- **불필요한 되묻기 4개:** 022 통제실 위험 감지 역할, 024 작업 중단·재개·대피 권한, 029 측정 위치·개소, 040 산소 및 유해가스 측정방법.
- **정답 페이지 불일치 3개:** 066 환기 부족 탱크 용접, 082 CO₂ 소화설비 오작동 방지, 083 CO₂ 경보 후 대피. 각각 34쪽, 61쪽, 61쪽을 선택했다. 관련 문서 표현은 있어도 기존 기준이 요구하는 절차와 조건을 충족하지 못했다.
- **정답 페이지는 찾았지만 필수 내용 누락 7개:** 098 보호구, 114·115·116 심폐소생술, 118·119·120 심폐소생술 반복·회복자세. 각 질문의 전체 필수 항목이 적절한지는 전문가 검수 대상이며, 이번에는 기준을 완화하지 않았다.
- **기존 기준은 통과했지만 추가 확인이 붙은 8개:** 014, 019, 027, 058, 080, 096, 106, 123. `과/와` 등의 연결 표현을 별도 질문으로 나누는 과정에서 의미가 불완전한 조각이 생기는 사례가 보인다. 모든 사례의 원인을 단정한 것은 아니다.

사용자가 이전에 지적한 **039 ‘어두운 밀폐공간 측정 전등은 어떤 걸 써야 해’는 이번 검사에서 통과**했다. 다만 040 일반 측정방법은 여전히 되묻는다. 일부 질문 개선을 검색 전체 해결로 판단하지 않는다.

## 실행 범위와 속도 해석

- 150개 원래 질문과 복합 질문의 부분 표현을 합쳐 197개 질문 벡터를 실제 계산했다. 화면은 벡터 계산과 질문 평가의 진행률을 따로 표시한다.
- 검색·답변 본문은 현재 Android의 순수 Kotlin 코드다. `KnowledgeRepository`의 ObjectBox, ViewModel, Android UI는 실행하지 않았다.
- 앱의 토큰 변환과 고정 가중치는 동일하지만 PC ONNX Runtime Node는 **1.21.0**, Android는 **1.22.0**이다. PC 세션을 재사용하며 실제 Android의 질문별 세션 개폐와 기기 메모리 조건을 재현하지 않는다.
- PC 추론 벡터를 먼저 계산한 뒤 Kotlin 검색에 전달했다. 보고서의 `pcMeasuredWorkSumMs`는 해당 질문에 필요한 추론 시간 합과 Kotlin 작업 시간의 합이다. **전송부터 실제 화면 표시까지의 응답 시간, Android 실측 시간, Gemma 생성 시간이 아니다.**
- 연결된 Android 기기가 없었다. Gemma 일반 지식/선택적 보충 생성, 음성, 실제 화면, 연속 질문, 발열·메모리, 전체 응답 1~2초 여부는 검증하지 않았다.
- 평가용 JUnit 작업의 성공은 150개 실행과 결과 기록이 완료됐다는 뜻이다. 질문 품질 실패 14개는 결과 파일에 그대로 남긴다.
- 평가 도구 추가 후 일반 JVM 회귀 검사도 실행해 기존 76개가 통과했다. 옵트인 실모델 평가 1개는 이 일반 실행에서 제외돼 총 77개 중 1개가 건너뛰기로 기록된다. 결과 화면의 실패 필터와 질문 상세 펼치기도 실제 브라우저에서 확인했다.

## 다시 실행하기

검색 모델 자산과 Gradle 의존성이 준비돼 있어야 한다. PC 평가에는 `onnxruntime-node`가 설치돼 있어야 한다. 이번에는 이미 설치돼 있던 `web/node_modules`의 런타임만 재사용했다. 웹 앱을 실행하거나 웹 코드를 변경하지 않는다.

```powershell
# 저장소 루트에서 실행. 아래 JDK 경로는 이 PC의 실제 설치 경로다.
$env:JAVA_HOME = 'C:\Program Files\Android\Android Studio1\jbr'
$env:GRADLE_USER_HOME = Join-Path (Get-Location) '.gradle-codex'
$env:FIELDGUARD_EVALUATE_150 = '1'
$env:FIELDGUARD_EVALUATION_DIR = 'tmp/evaluation-150-20261103'
New-Item -ItemType Directory -Force tmp/evaluation-150-20261103 | Out-Null
Copy-Item -LiteralPath tools/evaluation-150.html -Destination tmp/evaluation-150-20261103/index.html
.\gradlew.bat :app:cleanTestDebugUnitTest :app:testDebugUnitTest --tests com.minyook.sllm2.data.LiveQuestionEvaluationTest --offline --console=plain
```

별도 터미널에서 다음 명령을 실행하고 `http://127.0.0.1:8875/`을 연다. 로컬 PC에서만 접속하는 결과 화면이다.

```powershell
python -m http.server 8875 --bind 127.0.0.1 --directory tmp/evaluation-150-20261103
```

일반 단위 검사에서는 느린 150개 실모델 평가를 건너뛴다. 루트의 원래 메모장 질문 파일이 있으면 질문 순서와 내용을 고정 JSON 기준과 대조한다. 없으면 Android 계측 자산의 동일한 150개 질문을 사용한다. 평가 결과를 좋아 보이게 하려고 정답 기준이나 제품 검색 로직을 바꾸지 않았다.

## 다음 개선 순서

1. 의미가 연결된 명사구를 `과/와`만 보고 분리하는 문제와 필요 없는 되묻기를 먼저 고친다.
2. 용접·CO₂ 설비에서 절차 본문과 비슷한 사례 페이지를 구별하는 재순위 검사를 보완한다.
3. 질문 범위와 안전상 필수 연결 조건을 함께 평가해, 필요한 내용 누락과 불필요한 장문을 구분한다.
4. 현재 150개 기준을 보존하고 새로운 표현의 별도 평가 집합으로 개선을 확인한다.
5. Android 실기기에서 모델 준비→검색→첫 본문→생성 완료를 따로 측정하고, 문서 밖 생성 답변과 반복 질문을 검증한다.
