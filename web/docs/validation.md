# 웹앱 검증 기록

최종 검증: **2026-10-19** (iPhone용 같은 Wi-Fi HTTPS 준비). Windows Chromium과 연결된 Galaxy Tab S9 Ultra(SM-X910, Android 16)에서 확인했습니다. 아래 날짜별 기록은 변경 당시 결과이며, 현재 감독관 인증은 일일 숫자 6자리입니다. 실제 iPhone 검증 기록은 아닙니다.

## 2026-10-19 iOS 18.6.2의 AI 미지원 안내

- 사용자가 iPhone 13 Pro / iOS 18.6.2 / 같은 HTTPS 앱 주소에서 AI 다운로드가 차단된다고 보고했습니다. 기존 판정은 보안 컨텍스트·WebGPU·Worker 중 하나라도 없으면 포괄적인 미지원 문구만 표시했습니다.
- Apple/WebKit 공식 문서로 iPhone WebGPU의 정식 지원이 iOS 26부터이며 13 Pro가 iOS 26 지원 기종임을 확인했습니다. 따라서 사용자에게 지원되는 최신 정식 iOS로 업데이트한 뒤 재시험하도록 안내했습니다. 실제 iPhone 콘솔/AI 실행 성공을 관측한 것은 아닙니다.
- `capabilities.ts`로 공통 실행 조건과 HTTPS/WebGPU/Worker별 원인을 분리했습니다. 설정에서 조건 표시·iOS 업데이트 안내를 제공하고, 미지원 상태에서 모델/워커를 준비하지 않습니다. 실제 기능을 기준으로 판단하며 사용자 에이전트의 버전 숫자만으로 차단하지 않습니다.
- `npm.cmd test -- --maxWorkers=1 --no-file-parallelism`: **22개 파일 151개 통과**. 추가 8개는 HTTPS·WebGPU·Worker 원인 구분, iPhone/iPad 안내, 사용자 에이전트와 실제 기능의 분리, 런타임의 미지원 준비 차단을 검사합니다. TypeScript·Vite·PWA 빌드 성공.
- iOS 업데이트 후 iPhone 13 Pro의 모델 다운로드·GPU 메모리 적재·첫 토큰·발열·오프라인 생성 성공은 아직 확인하지 않았습니다. [지원 조건과 시험 절차](../../docs/IPHONE_TEST.md#iphone-ai의-별도-지원-조건)에 구분했습니다.

## 2026-10-19 iPhone 보안 연결 오류와 로컬 HTTPS 준비

- 기존 PC 사설 IP 4173 서버가 HTTP 200을 반환하지만 같은 포트의 HTTPS 요청은 TLS 오류(`ERR_SSL_PACKET_LENGTH_TOO_LONG`)로 실패하는 것을 재현했습니다. 일반 사설 IP의 HTTP에서는 이 앱의 최초 문서 읽기에 사용하는 Cache API·검증 API도 사용할 수 없어 전체 시험 안내를 HTTPS 기준으로 수정했습니다.
- `npm.cmd run iphone:test` 추가: 최신 PWA 빌드 후 같은 Wi-Fi용 설치 안내 HTTP 4172·공개 인증서 프로파일, HTTPS 앱/작업 API 4174를 실행합니다. 기존 서버와 데이터를 지우지 않습니다.
- 테스트 **21개 파일 143개 통과**. 추가 5개는 사설 IP 제한·실제 서버 인증서의 IP/호스트 검증·재실행/IP 변경 시 CA 유지·CA를 명시한 실제 TLS 연결·설치 경로의 개인키/파일/API 비노출을 검사합니다.
- TypeScript·Vite·PWA 빌드 성공. 실제 새 HTTPS 서버의 홈/API 200, COOP same-origin·COEP require-corp·Secure 세션 쿠키와 설치 페이지/프로파일 응답을 확인했습니다. 인증서 검증을 끄지 않고 개발 CA를 명시해 TLS 연결했습니다.
- 개발용 CA와 키는 `web/.local/iphone-https/`에만 유지하고 Git 제외를 확인했습니다. Windows/아이폰의 신뢰 저장소를 자동 수정하지 않았습니다. 인터넷 터널/외부 공개 배포도 수행하지 않았습니다.
- **아이폰에서 프로파일을 직접 설치하고 전체 신뢰를 켠 뒤 Safari·PWA·모델 동작을 확인하는 단계는 사용자가 수행해야 합니다.** 이 기록은 실제 iPhone 시험 성공을 의미하지 않습니다. [설치·신뢰·제거와 시험 절차](../../docs/IPHONE_TEST.md)를 제공합니다.

## 2026-10-16 작업자 요청과 감독관 승인 실시간 교환

- 이전 UI 검증 때 생성한 ‘권한 차단 검증용 가상 현장’의 종료 기록이 기본 감독관 상세로 열려 승인된 새 작업처럼 보이는 문제를 확인했습니다. 기록을 지우지 않고 ‘진행 중 / 종료 이력’으로 나눴습니다. 종료 기록은 과거 승인임을 표시하며 새 작업의 승인으로 사용하지 않습니다.
- 새 요청 화면이 선택했던 이전 작업의 진행 단계를 표시하던 문제를 수정했습니다. 새 작업은 요청·빈 점검·승인 없음으로 생성합니다.
- 요청/명령 POST와 인증된 SSE 변경 수신을 연결했습니다. SQLite 변경 번호를 1초마다 확인하고, 연결 실패 시 5초 확인·연결 복구 재조회로 보완합니다. 기존 15초 조회 구조를 교체했습니다.
- `npm.cmd test -- --maxWorkers=1 --no-file-parallelism`: **20개 파일 138개 통과**. `npm.cmd run build`: TypeScript·Vite·PWA 성공.
- 추가 자동 검사 12개: 독립된 HTTP 작업자/감독관의 요청 → 점검 저장 → 승인 → 투입 교환, 승인 전 투입 차단, 권한 없는 이벤트 구독 거절·다른 작업자 변경 번호 비노출, 열린 감독관 연결의 권한 회수, 두 SQLite 연결의 변경 감지, 보완/재요청/승인 취소, 스트림 수신·실패/복구·정리·미지원 대체, 종료 이력/새 요청/선택 보존을 검사했습니다.
- 실제 내장 Chromium 두 세션에서 감독관 0/5 점검·승인 버튼 잠김, 작업자 승인 전 투입 버튼 없음, 점검 저장 후에도 투입 대기, 수동 승인 후 작업자 화면 자동 갱신, 동의 전 투입 버튼 비활성, 작업자 투입 후 감독관 자동 수신을 확인했습니다. 감독관 화면을 열어둔 채 두 번째 요청이 자동 도착하고 새 요청 알림을 표시하며 읽던 작업 선택도 유지했습니다.

## 2026-10-15 태블릿 다국어 혼입 답변 대응

사용자 사진에서 한국어 답변에 영어·아랍 문자·데바나가리 문자가 섞이고 의미 없는 목록이 생성된 것을 확인했습니다. 사진의 생성량은 89토큰, 답변 한도는 1,536토큰이므로 출력 한도 도달에 따른 잘림으로 볼 근거는 없습니다. 태블릿 기종·브라우저·원시 추론 로그가 없어 기기별 원인은 아직 확정하지 않았습니다. [LiteRT-LM의 모바일 GPU 출력 손상 보고](https://github.com/google-ai-edge/LiteRT-LM/issues/3012)는 참고 사례이며, 해당 웹 모델·태블릿에서 같은 결함을 재현했다는 의미는 아닙니다.

- 한국어·근거·수치 보존 지시를 SDK의 시스템 메시지로 분리했습니다. 문서·질문은 사용자 메시지에 전달하며 원문 본문을 자르지 않습니다.
- SDK 샘플러를 Top-K 1, temperature 1, seed 0으로 명시해 점수가 가장 높은 토큰을 선택합니다. GPU 수치 오류를 교정하는 설정은 아닙니다.
- 원문·질문에 없는 문자권 혼입, 대체 문자·제어 문자, 심한 동일 문장 반복, 한국어 비중이 낮은 출력을 검사합니다. 기술 용어·단위와 근거에 있는 외국어 문자는 허용합니다.
- 생성 중 비정상 문자열은 확인 안내로 대체하고, 완료된 비정상 답변은 오류로 반환해 기존 원문 표시·저장 경로로 전환합니다. 저장된 과거 답변은 수정하지 않습니다.
- 사진 재현·정상 기술 용어·실제 SDK 설정 전달·비정상 스트리밍/최종 거부를 포함한 관련 6개 파일 **37개 테스트 통과**. 전체 **16개 파일 111개 테스트 통과**, 프로덕션 빌드 성공.
- Windows 내장 Chromium에서 수정 후 같은 질문 `산소 및 유해가스 측정방법 알려줘`의 한국어 스트리밍 완료·저장·25/27쪽 원문 연결을 확인했습니다. SDK 측정은 입력 1,348 / 생성 622 / 전체 1,970, 답변 한도 1,536토큰입니다. [PC 생성 결과 화면](screenshots/tablet-output-guard-pc.png)을 저장했습니다. 이 시험은 사진과 같은 다국어 혼입이 없음을 확인한 것이며, 답변 전체의 사실 정확도 검수나 해당 태블릿 재현 시험은 아닙니다.

이 검사는 눈에 띄는 출력 손상을 거르는 제한적인 검사입니다. 자연스러운 한국어로 쓴 오답이나 잘못된 숫자까지 검증하지 않으며, 실제 태블릿에서 정상 생성으로 복구됐다는 검증은 별도로 필요합니다.

기존 Android PDF 번들·음성 수정 사항은 웹 작업 시작 전부터 있던 변경이며 내용을 확인하고 함께 보존합니다. 최종 `git diff --check`를 통과했습니다. 웹 작업은 Android 화면·센서 동작을 재설계하지 않았습니다.

새 작업·점검·승인·투입/퇴장 기록에는 서버 연결이 필요합니다. 이전 로컬 테스트 작업은 읽기 전용이며 서버 승인으로 취급하지 않습니다. 문서·PDF·AI는 기존 오프라인 경로를 유지합니다. 현재 권한은 기기 세션 단위이며 개인 계정 로그인·현장 배정·계정 복구·외부 운영 배포는 남아 있습니다. 배포에서 정적 `dist`만 올리면 감독관/작업 API를 사용할 수 없습니다.

## 2026-10-15 모델 저장·실행 상태 구분

- 새로고침 후 나타나는 준비 과정은 기존 OPFS 모델 파일의 SHA-256 검사, 런타임 로드, GPU 실행 메모리 초기화입니다. 다운로드는 다운로드 버튼 경로에서만 수행하며, 파일이 남아 있으면 매번 모델을 다시 받지 않습니다.
- 설정에는 `모델 파일 저장됨`과 `실행 준비 중 / AI 사용 가능`을 따로 표시했습니다. 홈·질문 화면의 진행 표시도 `모델 확인 중 / 저장된 모델 불러오는 중`으로 구분하고 재실행 시 필요한 과정을 설명했습니다.
- 기존 무결성 검사와 엔진 초기화는 유지합니다. 이 변경은 실행 준비 시간을 단축하거나 새로고침을 넘어 실행 메모리를 유지하는 변경이 아닙니다.
- 전체 **16개 파일 112개 테스트 통과**, TypeScript·프로덕션 빌드 성공. 내장 Chromium의 새 페이지에서 다운로드 완료 버튼이 비활성화된 채 `모델 파일 저장됨`과 `실행 준비 중`, `저장된 모델 파일 검사 중 · 다시 다운로드하지 않아요`가 함께 표시되는 것을 확인했습니다. [저장·불러오기 상태 화면](screenshots/model-stored-loading.png).

## 2026-10-15 재접속 시 모델 전체 검사 비용 절감

- OPFS 모델은 최초 워커 실행에서 저장된 파일 전체의 SHA-256을 검사한 뒤 결과를 IndexedDB 모델 메타데이터에 보존합니다. 설치 직후도 저장된 바이트를 한 번 검사하며, 기존 다운로드 파일을 다시 받을 필요는 없습니다.
- 후속 실행은 파일 크기·수정 시각·최대 512KiB의 분산 표본 SHA-256을 확인합니다. 이전 결과와 같고 검증 기록이 7일 미만이면 2GB 전체 읽기를 생략합니다. 검증 기록 없음·이상·수정 감지·7일 경과 또는 파일 시각 확인 불가 시 전체 검사를 유지합니다.
- 검증 기록 갱신은 같은 설치인지 트랜잭션에서 확인합니다. 검사 중 다른 탭에서 삭제·교체한 모델을 되살리거나 새 설치에 옛 결과를 붙이지 않습니다. 파일 검증을 재사용해도 SDK 엔진 초기화가 끝난 뒤에만 `AI 사용 가능`을 표시합니다.
- 전체 검사와 빠른 표본 검사는 보장 범위가 다릅니다. 수정 시각이 유지된 표본 밖 손상은 다음 주기적 전체 검사 전까지 발견되지 않을 수 있습니다. 다운로드 전체 해시와 최초 저장 파일 전체 검사, 주기적인 재검사는 유지합니다.
- 워커의 실제 경과 시간으로 전체 준비·파일 확인·런타임·엔진 적재를 측정합니다. 화면에는 전체 준비와 파일 확인, 검증 재사용 여부를 표시하며 0.1초 미만은 반올림한 0.0초 대신 `0.1초 미만`으로 안내합니다.
- 전체 **17개 파일 124개 테스트 통과**, TypeScript·프로덕션 빌드 성공. 변경 파일·같은 크기 손상·같은 수정시각의 표본 손상·표본 밖 손상의 유효기간 후 발견·새 설치·삭제/교체 경쟁·준비 완료 시점·시간 표시 전달을 검사했습니다.
